# Issue #15：GPT-6.1 Sol 指纹与检测可靠性

核查日期：2026-10-10。需求来源：[is-gpt-nerfed Issue #15](https://github.com/kiyoakii/is-gpt-nerfed/issues/15)
以及用户在全程选择 Sol 6.1 时看到 Astra / 降配的实际反馈。实现决策见
[ADR 0004](adr/0004-conservative-fingerprint-resolution.md)，验收见 [VALIDATION.md](VALIDATION.md)。

## 当前结论

**现有随机数字指纹不能可靠区分 GPT-6 Astra 和 GPT-6.1 Sol。** 本次完成的是保守裁决与
来源分离修复，没有得到可正式上线的独立 Sol 指纹。把 Sol 数据加入模型库、复制 Astra 的
模板或仅增大置信门槛，都不能凭空创造稳定的区分信息。

Port.5 中，声明 Astra/Sol 6.1 且原始候选为 Astra 时显示中性的“无法区分”(`AMBIGUOUS`)。
它不表示已确认二者之一，更不表示排除了所有未知模型。若日志还记录了模型标识、力度或
上下文变化，界面单独显示原因与时间；不把这种被动证据说成数字指纹验证了服务端身份。

## 现有算法做了什么

生产模型库仍是原项目固定的 **16 类**，没有 `gpt-6.1-sol`。
代码为 [modeltrace_core.py](../plugin/skills/is-gpt-nerfed/scripts/modeltrace_core.py) 与
[nerfed](../plugin/skills/is-gpt-nerfed/scripts/nerfed)，库及来源见
[provenance.json](../plugin/assets/modeltrace/provenance.json)。

1. 让模型直接生成 1–355 的随机整数列表，不使用代码生成随机数。通常采集三份回答。
2. 解析并检查可用数量；用 355 维计数做平滑、平方根转换（Hellinger 特征）。另取四段数字
   的 16 桶分布与末位数字分布，补充顺序特征。
3. 按训练库的均值、尺度标准化，投影掉训练时识别的环境干扰方向，再与模型中心比较。
   顺序部分还融合环境模板；各候选分数在候选集合内标准化后合并。
4. 对多份回答的分数取平均，以对应回答数的 `beta` 做 softmax。UI 的百分比来自这个闭集
   归一化分数，不是对所有可能模型的身份置信概率。
5. 上层对已收录模型应用 top/声明概率门槛、至少两份回答和 0.5 个标准分的差值门槛。
   未收录模型没有可直接比较的声明行；被动 hard 证据则原本直接覆盖总裁决。

上述机制能检测某些**已收录模型在参考分布内**的行为差异，但有这些限制：

- **闭集强制归类。** 未知模型也会有第一名；softmax 及候选间 z-score 不具备分布外拒识。
  只有一个相近候选时，即使实际模型不在库中也可能接近 100%。更高百分比并不能解决它。
- **旧交叉验证不是现网准确率。** 原库的 1/2/3 答校准仅对应其参考数据和采样条件，不能
  推广成新模型、不同推理力度、Codex harness 或未来模型快照的保证。
- **行为受条件影响。** 系统/开发者提示、语言、格式、历史、力度和样本长度都可能改变
  数字偏好。临时 fork 减少对原会话的干扰，但仍沿用上下文，不等同于纯净独立 API 样本。
- **相关样本影响结论。** 同一会话连续回答、同一账号/时间/提示下重复采样不能直接按
  独立样本估算泛化准确率。三份长数字列表也不等同于数百个独立测试。
- **归因不等于能力或权重认证。** 选中的模型标识、日志元数据、行为指纹是不同来源；
  单独任何一种都不能由本软件独立证明服务端实际加载了哪套权重。

## 原作者、官方资料与讨论

[ModelTrace README](https://github.com/xqy2006/ModelTrace#readme) 已说明闭集概率的范围、
未知模型会落到已有候选，以及结果应作参考。其作者在
[Issue 26 的 9 月 30 日回复](https://github.com/xqy2006/ModelTrace/issues/26#issuecomment-5913940014)
说明直接加入 6.1 会严重混淆 Astra/Sol，特征差异不稳定；
[10 月 1 日回复](https://github.com/xqy2006/ModelTrace/issues/26#issuecomment-5925807408)
明确当前 6.1 会判到 Astra。这与此次复现一致。

所查 [OpenAI GPT-6.1 Sol 模型页](https://developers.openai.com/api/docs/models/gpt-6.1-sol)
描述其接近 Astra 的性能与较低成本；[模型选择资料](https://learn.chatgpt.com/docs/models?surface=app)
保留二者不同标识。**本次检索没有找到 OpenAI 对 ModelTrace 方法的官方认证，也没有找到
足以确认 Sol 与 Astra 同一权重或直接蒸馏关系的官方声明。** 性能相近不能推出训练谱系。

[Linux.do 的相关讨论](https://linux.do/t/topic/2968612) 同样报告 Sol 被归因到 Astra，
有用户猜测共同底座或蒸馏。前者可作现象线索；后者没有独立来源，不能作为确定事实。
Issue #15 中的“疑似蒸馏”也属于推测。论坛体验不能替代受控留出验证。

独立预印本 [One Token Is Enough](https://arxiv.org/abs/2607.10252) 表明输出分布在其测试中
能携带模型归因信号，但使用四种语言、多次单 token 查询和另一套评估，并非这里的三份
长列表。它支持继续研究行为指纹，不验证本项目的库、错误率或 Astra/Sol 可分性；也不是
OpenAI 官方背书。

## 公开候选 Sol 数据：实际离线复现

[ModelTrace PR 28](https://github.com/xqy2006/ModelTrace/pull/28) 提供 36 条 enrollment、
9 条 holdout 以及一条保留的失败尝试，来自贡献者声明的官方 Codex CLI 0.159.1 / `low`。
它保留 harness，挑战系统文本通过 developer 指令送入；样本没有独立服务权重认证。
采集覆盖 12 种环境，每环境三次；它与本机 `high` 的试验分别记录。

我们固定其提交 `1369ca7afca83db354eac5752d1e23f51bafd1b5`，保留 MIT 归属及 15 个原件的
URL/哈希。审阅原校验器及导入代码后，使用已有 Python/NumPy 环境实际运行，151.234 秒，
退出 0、完整性 PASS，生产库未修改。

| 候选实验 | 实际复现结果 |
| --- | ---: |
| Sol 单答交叉验证 | 20/36 |
| Sol 两答交叉验证 | 24/36 |
| Sol 三答交叉验证 | 6/12 |
| Sol 留出，单答 | 5/9 |
| Sol 留出，三答组 | 1/3 |
| Astra 三答交叉验证，加入 Sol 前 → 后 | 12/12 → 9/12 |

在当前 16 类生产库中，这 45 条公开样本的单答为 41 Astra、3 GPT-5.6 Sol、1 GPT-6 Luna；
15 个三答组全部 Astra。在固定 17 类上游基线中，结论相同。增加一个名字不等于获得
可分的类别；留出组过少，不能据此估算精确现网错误率，但足以否决直接正式启用候选库。

原件、实际 stdout、环境、全部结果和复现命令见
[研究说明](research/gpt61-sol/README.md)、
[实际校验运行](research/gpt61-sol/upstream-reproduction.json) 与
[来源哈希](research/gpt61-sol/provenance.json)。

## 本机补充试验与历史核查

按用户授权，在 Common 下只创建两个测试会话：`gpt-6.1-sol/high` 与 `gpt-6-astra/high`。
各直接回答三次原数字提示（中文 300、英文 300、中文 320），没有工具或代码代生成。
六份回答数量全部符合要求；两套库中**六个单答与两个三答组全部归因 Astra**。
已只读核对这两个会话的模型/力度元数据，并在完成后将二者归档。

匿名化样本与来源核对字段见
[samples.json](research/2026-10-10-codex-probes/samples.json)。原始数字可复查，未发布私人
会话标识、其他会话内容或凭据。每组仅三份、连续会话带历史、提示语言混合，没有新的
独立留出组；不能据此拟合可靠 Sol 中心、判断同一权重或计算识别准确率。

只读历史核查还发现：44 条声明 Sol 的本地 probe 中，27 条有效指纹原本为 `UNLISTED`，
9 条有效指纹与 2 条无可用输出记录为 `DOWNGRADED!`，另有 6 条 `INVALID`。
这 11 条 hard 总裁决全部来自被动覆盖：7 条 `max→xhigh` 力度记录、4 条
`Sol 6.1→GPT-5.6 Luna` 模型标识记录；相关事件早于检测完成约 0.23–2.51 小时。
36 条有效 Sol 指纹的第一候选均为 Astra。源码和安装版均精确保留 `6.1`，不存在把模型名
截成 `6` 的证据。上述汇总仅描述当时本机记录，不证明实际权重发生替换，也不确定设置
变化的操作来源。出于隐私，私人历史仅保留汇总，不纳入公开数值研究数据。

因此必须同时修复两个层面：承认 Sol/Astra 指纹重叠，并展示触发总裁决的真实证据来源
及时间。直接删除 hard 记录会丢掉另一类信息；把它继续混称为刚刚“指纹判降配”也不准确。

## Port.5 的行为与后续条件

| 声明与证据 | 指纹 | 总裁决 / 展示 |
| --- | --- | --- |
| Astra 或 Sol 6.1，原始第一名 Astra，无 hard 记录 | AMBIGUOUS | 中性“无法区分”，不告警、发声、暂停或宣称精确匹配 |
| 同上，有 hard 被动记录 | AMBIGUOUS | 保留总体被动告警，单独列出具体类型、原因与时间 |
| Sol 6.1，原始第一名其他模型 | UNLISTED | 模型未收录，不能据此断言改路由 |
| 其他已收录模型 | 原门槛 | 沿用原 MATCH/MISMATCH/SUSPICIOUS 规则及其统计限制 |
| 无可用数字回答，有被动记录 | INVALID | 指纹不可用，仍单独呈现被动记录 |

旧 probe/ledger 文件不改写；读取时投影当前解释，保留原始候选、分数、证据及旧裁决。
更新后需从新目录重新运行安装器、重启 Codex，才能同时刷新插件缓存后端与前端；只开
新窗口不保证 Codex 已加载新后端。历史无需清空，也无需花额度重跑才能修正展示。

要正式增加 Sol，应先用更多独立新上下文控制 harness、语言、格式、力度、账号与采集
时间，预先划分留出评估，报告双向混淆和未知模型误接受率，再验证拒识或分层分类方案。
本次没有证据支持只靠“推算”或放大 softmax 差值上线。数值算法仍约毫秒级；实际采样
涉及模型生成，慢的主因仍是推理链路，参见 [性能分析](PERFORMANCE.zh-CN.md)。
