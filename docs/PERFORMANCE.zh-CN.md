# 检测原理与延迟分析

2026-10-10 的离线实测表明：三份公开夹具回答的完整指纹归因加裁决中位耗时为 **11.7 毫秒**。
现有本机历史中，18 次完成的三样本 fork 探测中位耗时为 **189.7 秒**，时间几乎全部落在等待探测 turn 完成的区间。
优化统计评分不会明显缩短这类探测；更值得关注的是模型生成、历史上下文、服务端等待和必要的重试。
现有计时没有首 token 或服务端阶段数据，不能进一步给这些因素分配准确占比。

本文代码基线为 `d55ee05` 及本轮工作副本。基准工具会输出各输入源码的 SHA-256；下文行号用于定位，函数名是更稳定的索引。
没有修改探测提示词、指纹库、评分算法或探测默认配置。

## 两条检测路径

**被动扫描**读取 Codex 的本地 JSONL rollout，比较 `turn_context` 中的模型与推理力度、
`thread_settings_applied` 中的显式设置变化，以及 `token_count` 中的上下文窗口变化。
它记录变化证据，不发送模型请求，也不直接观察服务端权重。
`scan_rollout` 保存字节游标，只读取上次完整换行之后的新数据；文件没有增长时只检查文件大小。
增量调用默认最多读取 64 MiB，`scan_full` 使用新状态且默认最多读取 256 MiB；都不是无限制读完整个文件。
源码见 [nerfed 的扫描函数](../plugin/skills/is-gpt-nerfed/scripts/nerfed)：`new_scan_state`、`scan_rollout`、`scan_full`。

**主动指纹**默认建立三个临时 fork，各自要求模型直接选择 **292–332 个 1–355 的整数**。
允许重复，禁止排序、平衡频数、工具、代码与其他模型代答；语言随机选择中英文。
这里测量的是模型生成数字的偏好，而非数学答题能力或通用智能。
同一提示下不同模型在值频率、序列位置和尾数分布上的偏好，与预先登记的模型中心进行比较。
源码见 [codex_appserver.py:29–37](../plugin/skills/is-gpt-nerfed/scripts/codex_appserver.py#L29) 的 `PROMPTS`、`COUNT_RANGE`。

本项目固定的 `unified_bank.json` 为 16 个候选模型。上游当前 README 的模型数量不能替代本项目库的实际内容。
归因是库内候选之间的比较：高概率表示更接近该库中的候选，不等于证明服务端使用了某一组权重。
未登记模型、提示环境变化和输出分布漂移，都可能被分配给已有候选。

## 数字如何变成裁决

1. `parse_numbers` 取最长的一段有效数字，字母分隔会切段，只保留 1–355。
   回答至少要有 `max(80, ceil(期望数量 × 0.55))` 个数字才被接受。
2. 值频数加 0.5 平滑后开平方，得到 355 维 Hellinger 特征。
   另一组特征把序列分为四个位置块，每块 16 个值域桶，再加 10 个尾数桶，共 74 维。
3. 使用库内的均值、尺度、干扰方向和模型中心进行标准化、投影与余弦比较。
   固定库的两个特征组各有 2 个干扰方向，位置特征另有 12 组环境中心。
   两组标准化分数以 0.75 / 0.25 融合，再对有效回答的模型分数求均值。
4. 根据有效回答数选择库内校准温度，softmax 得到 16 个候选的相对概率。
   超过三份回答时仍使用三答校准项，不能据此声称已经获得独立的六答校准。
5. `assess` 比较声明模型与最高分候选。默认 `MISMATCH` 同时要求：最高候选概率至少 0.8、
   声明模型概率最多 0.2、两者融合分数差至少 0.5σ，以及至少两份有效回答。
   一份回答即使显示很高概率，也只能把不一致报告为 `SUSPICIOUS`。
   被动硬证据会优先产生 `DOWNGRADED!`，这不依赖指纹分数。

算法源码见 [modeltrace_core.py](../plugin/skills/is-gpt-nerfed/scripts/modeltrace_core.py)：
`parse_numbers` 第 29 行、`hellinger_feature` 第 88 行、`ordered_block_feature` 第 103 行、
`robust_score_numbers` 第 139 行、`analyze_global_outputs` 第 175 行。
裁决源码为 [nerfed 的 assess](../plugin/skills/is-gpt-nerfed/scripts/nerfed)，以及常量 `MARGIN_SIGMA`。

固定库中的分组交叉验证数据如下，数字直接来自 JSON。它们是登记数据上的验证结果，不能作为未来真实会话准确率的保证。

| 有效回答数 | beta | 库内验证命中 | 库内验证准确率 | 当前裁决限制 |
| --- | ---: | ---: | ---: | --- |
| 1 | 7.27758 | 549 / 576 | 95.3125% | 不允许仅凭指纹产生 `MISMATCH` |
| 2 | 12 | 574 / 576 | 99.6528% | 仍须通过概率与分差门槛 |
| 3 | 12 | 192 / 192 | 100% | 仍须通过概率与分差门槛 |

源码注释中的单答“95.5%”是近似/历史文字；本表采用当前固定库的 `549 / 576`。
该方法没有通用能力题目、权重访问或计费核验，因此不能用来量化能力下降、证明商业欺诈或评判模型整体能力。

## fork、并行与等待的实际含义

`run_fork_probe` → `probe_round` → `codex_appserver.probe_thread` 构成默认主动调用链。
一次 round 启动一个私有 app-server，执行握手、读取一次会话元数据、列出最近 turn、
在最新可用的已结束 turn 上创建第一个 fork，再在同一个 turn 上创建其余 fork。
**三个 fork 复用同一个 app-server**，没有为每份回答另起服务进程。

`run_turns` 第 375 行的默认 `parallel=True` 会依次发送并等待各次 `turn/start` RPC 的确认，
随后统一收集所有 fork 的通知；它不会等待第一份模型回答完成后才启动第二份。
因此 fork 创建和启动确认是串行控制步骤，模型回答阶段默认并发。
`parallel=False` 才是在前一份完成后启动下一份。
真实端到端耗时通常更接近最慢的一份回答加控制开销，具体还受服务端并发与资源争用影响。

fork 参数包含 `lastTurnId`、`ephemeral=True`、`excludeTurns=True`，并保留目标模型、provider、cwd 和推理力度。
`thread/read(includeTurns=False)`、`thread/turns/list(itemsView="notLoaded")` 与 `excludeTurns`
避免把大量 turn 内容返回客户端；**这些字段不表示模型获得空历史上下文**。
[官方 app-server 协议](https://learn.chatgpt.com/docs/app-server) 的 `thread/fork` 说明：
指定 `lastTurnId` 时复制截至该 turn（包含该 turn）的历史；`ephemeral` 控制临时 fork 的存储生命周期。
正在进行中的 turn 不包括在 fork 中。

`fresh` 则调用 `thread/start` 创建全新临时会话，没有原会话历史。
它仍有会话所需的基础指令、配置和提示，因此也不等于输入只有那一条数字要求。
fresh 回答的是“新会话此刻获得什么”，fork 回答的是“这个已有会话的设置与历史环境下获得什么”；二者不能直接互相替代。
对应源码为 `read_thread` 第 190 行、`fork_params` 第 260 行、`probe_thread` 第 405 行、
`start_ephemeral` 第 487 行、`probe_fresh` 第 505 行。

等待和重试可能让总耗时明显超过单个超时值：

- 当前 CLI 默认 `probe_timeout_s=300`，`queries=3`、`parallel=True`、`confirm_uncertain=False`。
  `codex_appserver` 低层函数签名仍有 180 秒默认值，但正常 CLI 调用明确传入当前配置值。
- 若最新 turn 仍在运行，会尝试最多三个已结束候选；没有可 fork 候选时，默认最多等待约 600 秒，按最多 10 秒间隔轮询。
  这段等待发生在 fork 回答阶段的 300 秒 deadline 之前。
- fork 路径的回答 deadline 在首个 fork 成功之后设置，包含其余 fork 创建、启动和收集；
  fresh 路径的 deadline 从本轮开始计算，包含 app-server 启动与新会话创建。
  RPC 超时、超时后的中断和服务进程清理还有各自时间预算，故它不是硬性的整项总时限。
- `probe_round` 对符合传输错误条件的失败最多自动重试一次，重试前等待 8 秒。
  完整 runner 会重新启动 app-server，并重新读取元数据、创建 fork。
- `top_up_timeouts` 对未在 deadline 内返回的缺失样本最多补做一次，目的是避免只让较快回答决定归因。
  补做仍经过 `probe_round`，因此也可能遇到自身的传输重试。
- 只有显式开启 `confirm_uncertain`，第一轮 `SUSPICIOUS` 才追加一轮回答。默认没有这轮额外开销。

这些行为分别见 `fork_at_latest_finished_turn`、`probe_round`、`top_up_timeouts`、`needs_confirmation`。
不能用“三答 × 单次超时”或“每次最多 300 秒”概括全部等待情况。

## 可复现离线基准

运行 [tools/benchmark_probe.py](../tools/benchmark_probe.py)：

```powershell
python -B tools/benchmark_probe.py
```

默认只向 stdout 输出 JSON，可自行重定向保存。工具只使用 Python 标准库，直接导入 `modeltrace_core`；
对主 CLI 的裁决和扫描函数使用白名单 AST 提取，不执行 CLI 顶层代码。
方向分类使用空模型目录，扫描显式传入空隐藏模型集，因此不会读取用户模型缓存。
它不导入主 CLI、不读取用户会话、不启动真实 Codex，不改变调用者环境变量或任何真实 home。
fake 子进程的 `CODEX_HOME` / `NERFED_HOME` 仅指向自动清理的临时目录，继承环境中的 fake 故障标记会被移除。
临时文件只含公开夹具派生数据。

可调参数为 `--repeats`、`--warmup`、`--process-repeats`、`--fake-repeats`。
后两项设为 0 可关闭对应子进程测量，例如快速检查 JSON 接口：

```powershell
python -B tools/benchmark_probe.py --repeats 3 --warmup 1 --process-repeats 0 --fake-repeats 0
```

## 现有本机记录的匿名对照

主代理只读汇总了已有本地记录，没有为本次分析新发起模型推理。统计区间为
2026-10-09 11:17:15 UTC 至 2026-10-10 03:22:54 UTC；文档只保留汇总值，不保存会话标识、私有路径、模型选择或回答。
18 次完成的 fork 探测均为 `queries=3`、`rounds=1`，共 54 份回答；另有 1 条 failed 和 1 条 running，不纳入完成时间统计。

三份 fresh 输入均为 22,626；cached 最小 / 中位 / 最大为 0 / 0 / 22,528，

`turn.elapsed_s` 包含启动确认、生成与等待客户端收到完成事件的时间，不能进一步区分网络、服务端排队、
推理、可见生成和历史 prefill。离线计算与历史记录也来自不同运行时刻，不能把两者直接当作精确的成本分摊。

## 加速取舍

| 方向 | 可能收益 | 需要保留的边界 |
| --- | --- | --- |
| 三答改为两答 | 少一次模型请求，降低资源消耗，可能减少尾部等待 | 两答仍可通过 `MISMATCH` 门槛；库内验证较三答弱。默认并行下不能承诺耗时减少三分之一 |
| 三答改为单答 | 最少请求，适合先获得初步归因 | 当前裁决禁止单答产生指纹 `MISMATCH`。不能降低置信门槛补偿样本缺失 |
| 分阶段先一答、需要时再补 | 明确匹配时可能较快 | 不确定案例增加串行波次；早停会改变样本选择条件，需要专门校准验证 |
| 保持当前并行 | 让总时间接近最慢回答而非三份之和 | 当前已经实现；更高并发仍可能受到服务端资源争用影响 |
| 跨 round 复用 app-server / 已核验元数据 | 避免重试或确认轮重复握手和 read | 当前同一 round 已复用。需要处理会话设置变化、进程失效与通知归属；现有记录显示控制开销远小于回答等待 |
| 调整超时与重试展示 | 让长等待原因更可见 | 缩短超时会偏向较快样本；补样本原本是为减轻这种选择偏差。不能把控制等待隐藏成算法慢 |
| 优化评分或 JSON 载入 | 节省毫秒级 CPU 时间 | 当前已有 bank 缓存；对约 190 秒探测收益有限，不值得默认引入重型依赖或重写数值内核 |

不应通过降低被测会话的推理力度来宣称“相同探测更快”：fork 显式继承并检查原 effort，改 effort 会改变被测条件。
也不应把同一个 fork 连续问三次当作三个独立 fork，后面的回答会继承前面的数字任务。
修改提示词、数字数量范围或 bank 更需要重新登记与校准，本次没有这样做。

若要进一步确定瓶颈，下一步应增加本地分段计时：进程启动与握手、元数据读取、各 fork 创建、
`turn/start` 确认、首个回答事件、最终消息、`turn/completed` 和清理。
只记录阶段时间与 token 汇总即可，无需保存私有答案。
客户端阶段数据仍只能缩小范围；要精确分开服务端排队、推理和 prefill，还需要服务端可观察数据。
